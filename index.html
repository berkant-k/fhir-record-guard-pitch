FHIR Record Guard

Can this FHIR record be safely and reliably used?

It reads one patient's Patient/$everything bundle and returns a verdict with the evidence behind it. Rules decide. AI explains. A person approves.

✓Safe to use
No critical or high-severity findings
!Use with caution
At least one high-severity finding
✕Do not use
At least one critical finding

Valid is not the same as usable

A FHIR server accepts a record when it is well formed. It does not ask whether the record makes sense. Each of these passes validation:

  • Amoxicillin is actively ordered for a patient with a recorded penicillin allergy.
  • Apixaban and warfarin are both active at the same time.
  • The date of birth is in 2031.
  • A Qatar ID has the wrong length, or contains letters.
  • A heart rate of 420 is recorded as a final result.
  • Appointments are still booked two years after they took place.

How it works

  1. Fetch

    Patient/$everything from the FHIR server, following paging links.

    Code

  2. Check

    20 deterministic rules and a weighted completeness score.

    Rules

  3. Decide

    The verdict follows from the worst finding. Same record, same answer.

    Rules

  4. Explain

    Plain-language summary, a suggested review order and a next step for each finding.

    AI · advisory

  5. Review

    A reviewer approves or rejects every drafted action.

    Human

  6. Record

    DetectedIssue, Task and Provenance, sent to the server only after the reviewer confirms the exact JSON.

    Human

Rules

  • Find every problem.
  • Set severity and the verdict.
  • Cite the resources as evidence.
  • Route each finding to a reviewer role.

AI

  • Explains, orders and summarizes.
  • Never sees names, identifiers or birth dates.
  • Has no field for severity or verdict.
  • Every claim must cite a finding, or it is dropped.

Human

  • Approves or rejects each action.
  • Sees the FHIR resources before anything is sent.
  • Is recorded in Provenance as the verifier.

What a reviewer sees

What it checks

Clinical safety

4 rules
  • Allergy and medication conflict
  • Duplicate anticoagulants
  • Implausible vital signs
  • Order with no dosage

Identity

4 rules
  • Future date of birth
  • Several patients in one record
  • No identifier and no name
  • Identifier format, such as an 11-digit Qatar ID

Completeness

5 rules
  • Missing demographics or allergy information
  • No phone or email
  • Upcoming appointment with no patient or service type
  • Family history with no relationship or condition

Technical

5 rules
  • Dangling references
  • Completed events dated in the future
  • Code format and missing display text
  • Stale booked appointments

Billing

2 rules
  • Duplicate claims
  • Service dates in the future

It does not re-run structural FHIR validation, because the server already did that. These rules cover what validation cannot see. Running the rules on larger real-world bundles removed false alarms, such as references to practitioners that $everything never returns.

Rule Copilot

For the people who write validation rules. It looks for patterns across many records and proposes new rules, then tests its own proposals.

  1. Code summarizes the patterns across records. No patient data leaves.
  2. AI proposes rules as FHIRPath, with test cases and the statistics that motivated them.
  3. Code runs each rule against its own tests and against the real records. Failures are thrown out. The rest show a dry run, such as “would flag 3 of 5 patients”, with a warning when a rule looks too broad.

Nothing is activated automatically. A profile author reviews each proposal.

Status

A working prototype, built before the hackathon, on synthetic data. There is no login yet, so it is not for real patient data.

Known limits

  • The clinical rules are narrow (the penicillin class, anticoagulants) and need a clinician's review before real use.
  • AI text can add general medical context that is not in the finding. That is why it is labelled advisory.
